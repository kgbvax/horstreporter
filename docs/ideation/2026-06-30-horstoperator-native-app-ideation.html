Grounding Context

What it is. HorstReporter is a single Go 1.24 binary that ingests the PSK Reporter MQTT firehose of amateur-radio reception reports (FT8/FT4 spots), keeps a rolling in-memory history in a hub, and streams matched spots over SSE to a browser SPA (Leaflet + Bootstrap + Turf, ~9.8k LOC, with an in-progress Svelte migration). It gives operators real-time HF propagation awareness — point at your callsign/grid and see which bands are open, how far signals reach, best directions, and a per-band "DX Potential" score against a historical baseline, all without transmitting.

A native operator app already half-exists. cmd/horstoperator-agent uses fyne.io/systray for a Windows tray with a 3-colour status icon, a menu, PowerShell toast notifications, scheduled-task restart logic, a local-first reverse-proxy on 127.0.0.1:9955, and a Health()/runDiagnostics() readiness model. But it is Windows-only, and its "Open UI" action still just opens the browser. There is no native rendering and no macOS/Linux presence.

The core is already browser-independent. mqtt.go, hub.go, spot.go, dx_conditions.go, and hot_bands.go are largely pure Go: scoring takes a history []MQTTMessage slice plus now, and Postgres is optional behind store == nil guards. The load-bearing coupling is that the Hub exposes no Subscribe/Unsubscribe API — the only way to register a client and drain its channel is inlined inside the SSE handler in server.go, interleaved with event-stream framing and gzip.

Where the weight is. The desktop path inherits server-grade defaults: a required Postgres (-dx-postgres-fail-fast defaults true), a subscription to the entire global pskr/filter/v2/# feed, an ~80 MB dx_baseline.json loaded at runtime, and a 5.3 MB embedded static tree (2.9 MB of which is world.geojson, plus vendored Leaflet/Bootstrap/Turf). The canonical map math — azimuthal-equidistant projection, great-circle interpolation, Maidenhead locator — currently lives in JavaScript and is duplicated and divergent versus the Go side (Go's locator returns a square centre; JS returns corner bounds). The 2026 native-Go landscape (Gio, Ebiten, energye/systray, caseymrm/menuet, Paho MQTT channel-feeds) makes a small always-on native client genuinely feasible — Tailscale's menubar GUI is the gold-standard precedent.

1.

The horstcore seam — give the Hub a Subscribe() and let the GUI read spots in-process

Axis 3 · Core reuse & data plane Confidence 90% Complexity High
Description

Carve mqtt/hub/spot/dx into a reusable horstcore module and add a real Subscribe(targets) (<-chan Spot, cancel) / Unsubscribe API to the Hub. The native render loop ranges over that channel directly; SSE, JSON marshalling, gzip, and the loopback server become one optional adapter layered on top of the seam rather than the seam itself.

Basis
direct: Verified — hub.go exposes only broadcastMsg; client registration is inlined in server.go (~lines 94–155); go.mod already carries replace dxlens => ../dxlens as a sibling-library carve-out precedent.
Rationale

This is the single structural blocker. While the only path to a spot is an HTTP handler, "native" is a browser tab in disguise wrapped around a localhost server. Cutting this seam once converts an HTTP-shaped product into a library-shaped one and unblocks the renderer, the menubar instrument, in-process scoring, the recorder, and any future HorstSuite frontend.

Downsides

Largest refactor in the set; touches the hottest code path. Needs care around the history-backfill scan and client lifecycle currently entangled with the flusher. Package globals (hub, dxBaseline, logLevel) must become injected dependencies, which ripples through main.go wiring.

2.

The lean embedded profile — your horizon, not the planet; no database; a baseline that grows itself

Axis 5 · Footprint & distribution Confidence 85% Complexity Medium
Description

Three server-era weights that sabotage "small + always around," removed together as one desktop profile: (a) subscribe to topic patterns scoped to the operator's target instead of the global pskr/filter/v2/# firehose, letting the broker filter; (b) default to in-memory and compile Postgres out of the desktop build via a build tag; (c) drop the ~80 MB dx_baseline.json and self-bootstrap a small per-target baseline from the operator's own live stream via the existing Observe() accumulation.

Basis
direct: Verified — mqtt.go:91 subscribes pskr/filter/v2/# ("Subscribed to global PSKReporter MQTT feed"); the topic encodes …/{senderCall}/{receiverCall}/{senderLocator}/{receiverLocator}. -dx-postgres-fail-fast defaults true (main.go:195) yet store == nil is first-class. dx_baseline.json is 84 MB loaded at runtime; Observe() is pure in-memory accumulation.
Rationale

An always-on app cannot demand a Postgres daemon, parse every FT8 spot on Earth to watch one grid, and load 80 MB of strangers' history at startup. The code already proves each weight is optional; the desktop profile is mostly removal, which compounds into a deployable single-file app that idles cheaply on a laptop or a shack Raspberry Pi.

Downsides

Verifier caveat: MQTT cannot prefix-match within a topic segment, so the "neighbouring squares / reachable horizon" case requires enumerating exact locator squares, not a single wildcard. A self-bootstrapped baseline starts at low confidence (grey) and needs run-time before scores are trustworthy — a cold-start window the global file avoided.

3.

A native vector renderer — azimuthal-first, no tiles, no browser, one canonical Go geo package

Axis 2 · Native rendering Confidence 80% Complexity High
Description

Build the map/azimuth surface on Gio's immediate-mode GPU vector renderer (Ebiten is the alternative), driving both projections from a single canonical Go geo package — horstgeo — that owns AEQD project/unproject, great-circle interpolation, Maidenhead locator, the DXCC palettes, and the grey-line terminator. Ship a quantized low-poly coastline instead of the 2.9 MB GeoJSON. Start with the azimuthal (PPI radar-scope) framing: spots are blips that fade with Spot.AgeSeconds, range rings show distance, bearing shows great-circle azimuth.

Basis
direct: AEQD is self-contained math in azimuth-runtime.js; world.geojson is 2.94 MB; Go locator returns centre (spot.go "Center of field") vs JS corners — a real divergence. external: Gio (gioui.org) — tiny GPU-vector binaries, proven by Tailscale's menubar and gotraceui.
Rationale

"No webviews" is decided here. A native renderer must reimplement the map math regardless — doing it once in Go (not a fifth fork in a fifth language) retires the JS↔Go drift permanently and gives scoring and rendering one shared geodesy. The radar-scope framing maps 1:1 onto an egocentric "who can hear me, which way, how far" question the data was always about.

Downsides

Largest build effort and a one-way-door toolkit choice (Gio vs Ebiten vs Fyne) for the whole rendering future. Dropping world.geojson means sourcing a smaller coastline — it is reference geography, not tiles, so "drop it" really means "replace with a lighter vector," not "no land." A tiled Mercator mode, if wanted, still needs a tile cache and Web-Mercator math.

4.

A cross-platform native presence shell — one Presence interface, not a Windows-only tray

Axis 1 · Always-on presence Confidence 85% Complexity Medium
Description

Define a small Presence interface — SetStatus(running/warn/error), SetTitle(live), Notify(title, body), OnMenu(...) — implemented by the existing Windows tray and by caseymrm/menuet (macOS NSStatusBar, SMAppService start-at-login) and energye/systray on Linux. Keep the agent's tested ops scaffolding — Health()/runDiagnostics() readiness, clean restart, login-at-startup, diagnostics menu — and replace only the single "Open UI → browser" action with "open the native window."

Basis
direct: tray_other.go logs "-tray is only supported on Windows; running headless"; the Windows openURL action reverse-proxies the browser UI; Health() already yields the green/amber/red signal. external: fyne.io/systray is already a dependency and is cross-platform — the Windows-only restriction is self-imposed via build tags, so this is lower-effort than it looks.
Rationale

"Always around" is currently a Windows-only promise that doesn't exist for roughly half of hams' machines. An interface seam makes macOS/Linux presence an implementation, not a rewrite, and a surprising amount of supervisor/readiness/restart plumbing already survives the native pivot — the work is far smaller framed as "replace the render target" than "build an agent."

Downsides

Tray libraries carry platform-specific packaging realities (macOS wants an .app bundle + LSUIElement; Linux DBus StatusNotifier variance). Whether one Gio app owns both tray and window, or tray (menuet) composes with a Gio window, is an architecture decision that interacts with idea 3's toolkit choice.

5.

The menubar is the instrument — a live title and glyph, not a window you open

Axis 4 · Glanceability & interaction Confidence 85% Complexity Low
Description

Render the richest signal the product computes — the green/yellow/red overall status plus the best band and the hot-band trend glyph — as the menubar text itself, e.g. 20m ↗ green, updating in place. Optionally draw a tiny per-band histogram into the ~22 px status icon (one bar per band, height = DX score, tint = band colour). The map window becomes the rare drill-down; most days the operator reads one line and never opens anything.

Basis
direct: classifyOverallStatus returns green (≥65) / yellow (≥35) / red / grey (dx_conditions.go); hot-band glyphs ★/↗/↑ with reasons exist in hot_bands.go + hot-band-indicator.js; today's tray icon is only tri-state health. external: menuet live NSStatusBar titles; the "live title + small menu" pattern is loved (Tailscale, "Why Awake?", iStat Menus / MenuMeters for the in-glyph histogram).
Rationale

"Scan the whole spectrum in a few seconds" is the product's core promise; a live menubar title delivers it in zero seconds and zero clicks — the literal payoff of "always around." Because scoring is a pure in-process function, the same evaluation drives the title, the dropdown, and notifications from one call per cycle.

Downsides

Deciding exactly what belongs in the always-visible title vs the dropdown is a genuine product call — too much and it's noise, too little and it's a status dot. The in-glyph histogram is fiddly at 22 px and platform-specific. Depends on idea 1's in-process feed to be cheap.

6.

Sentinel mode — the app watches the operator, not the reverse

Axis 1 · Always-on presence  /  Axis 4 · Interaction Confidence 80% Complexity Medium
Description

Invert "operator opens a tab." The default is a silent background daemon that fires a native OS notification when a band actually opens — driven by the existing hot_bands classifier (surprise / dx-surge / rising). Gate firing on state transitions, not polling, so a steady band stays quiet (calm-technology policy) and alert fatigue doesn't set in. Let the operator author their own rules over the in-process stream ("10m, bearing 290–320°, rate > 3× baseline"), and optionally surface events as audio — a soft CW-style chirp, pitch mapped to band — since hams decode tones natively and their eyes are on the rig.

Basis
direct: hot_bands.go defines surprise (baseline ≤0.1 & ratio ≥5×), dx-surge (≥5000 km), and rising as hardcoded gates; OVERVIEW.md roadmap asks for "per-band opening alerts … browser alert or audio cue when a quiet band spikes above baseline"; notify today is Windows-only PowerShell; SpotsPerMinute exists. reasoned: a ham shack and a trading desk both watch a high-rate firehose the operator can't stare at — pre-declared conditions + push on match is the proven shape.
Rationale

6m/10m openings are short and unpredictable — exactly the case where a closed browser tab fails the operator. An always-on native notifier turns a roadmap aspiration into the feature that justifies running this 24/7, and answers "if the operator never opens a window all day, did the app still do its job?" with yes.

Downsides

Alert cadence, dedup, and quiet-hours are make-or-break — get them wrong and it's muted on day one. User-authored rules add a config surface and a small rule-evaluation engine. The audio channel is a genuinely different mode some operators will want off by default.

7.

Close the loop — from "best DX is at 47°" to one-tap antenna command

Axis 4 · Glanceability & interaction Confidence 65% Complexity Medium
Description

The scoring engine already computes a DominantDirection per band; the operator panel already commands a PSTRotator. A native app can fuse these in-process — surface "best DX is at 47°" and offer one-tap "turn the antenna there" — with no browser, no SSE, no reverse proxy. The propagation viewer becomes a station controller, collapsing the viewer and the operator-agent into one native loop.

Basis
direct: Verified — per-band DominantDirection exists (dx_conditions.go); opmode.js drives a real PSTRotator over the agent's local API; OVERVIEW.md describes "click spot → command rotator." Today this requires the agent's loopback reverse-proxy to the browser UI — a native app removes that whole layer.
Rationale

It shifts the product from "tells you where DX is" to "points your antenna at it" — a category change the browser architecture actively obstructs (it needs the loopback proxy bridge). And it collapses two apps plus a proxy into a single native loop.

Downsides

Rig/rotator control is safety- and hardware-sensitive — accidental antenna movement is a real failure mode, so it needs guardrails and explicit confirmation. Only relevant to operators who run a rotator, narrowing the audience. Depends on the native shell (ideas 1, 3, 4) to remove the proxy it currently relies on.
